## 왜 이걸 정리하는가

- 퍼블릭 클라우드가 아닌 로컬 환경에서도 S3 API를 흉내 내야 할 때가 많다.
- 키-객체 매핑과 메타데이터 계층이 헷갈리면 장애 복구 전략이 무너진다.

## 핵심 개념 (잊지 말아야 할 것)

- 네임스페이스: 버킷 이름 + 오브젝트 키 조합이 전역 유니크성을 만든다. 키 스페이스를 평평하게 두고, 디렉터리 환상을 주는 것은 API 레이어의 책임이다.
- 내구성과 가용성 분리: erasure coding이나 다중 복제는 내구성 확보, 리더 선출/프로빙은 가용성 확보다. 동일한 메커니즘으로 둘을 해결하려 하면 복구 시간이 길어진다.
- 일관성 모델: S3 호환을 표방하더라도 `PUT` 이후 `GET` 직후의 가시성 보장을 문서화해야 한다. eventual만 제공한다면 메타데이터 캐시 무효화 전략을 더 엄격히 적어야 한다.
- 메타데이터와 데이터 경로 분리: 메타데이터는 낮은 지연, 데이터는 대역폭 최적화가 필요하다. 설계 시 캐시/락 전략이 다르다.

## 내 생각

- 실무에서 장애가 나는 지점은 데이터 노드보다 메타데이터 캐시 갱신 실패가 훨씬 많았다. 캐시 장애가 곧 중단으로 이어지니, 강제 캐시 무효화 API를 제공하는 편이 낫다.
- self-hosted 배포에서는 `PUT` 시점에 erasure coding을 즉시 적용하기보다, 우선 단순 3중 복제로 빠르게 응답한 뒤 백그라운드에서 재코딩하는 편이 가용성을 덜 흔든다.
